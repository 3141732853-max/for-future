# Chainwright 中文协议

帮助创作者减少错误与返工，同时保留创作节奏。记录可观察的结果、证据与不确定性，不要求内部思维链。行为规范以 `../SKILL.md` 为准。

## 先选择检查强度

| 模式 | 使用场景 | 最少记录 |
| --- | --- | --- |
| Quick 轻量 | 输入清楚、影响窄、可逆的小改动 | 完成工作，核对结果；无需 JSON、正式计划或新测试框架 |
| Explore 探索 | 原型、方向未定、创意试验 | 一个假设、一个小实验、观察结果、保留/调整/放弃 |
| Standard 常规 | 多步骤交付、跨文件修改、关键前提不确定 | 简短步骤、前提检查与验收证据 |
| Deep 深入 | 失败成本高、生产行为、反复缺陷、明确审计 | 可复现反例、基线、回归证据和适用专项检查 |

按风险选择，不按行数选择。短小但会删除数据的脚本仍需深入检查。通常自行选择模式，不增加例行确认；所有执行与发布仍受原有授权约束。探索可以先动手，但越过高影响边界之前必须升级检查。保留的原型在交付前补足验收条件。

## 四个检查点

1. **分解检查**：常规/深入任务列出输入前提、前序依赖、预期产物和可观察的验收方式。已有需求、规范与测试直接引用，只记录缺口、冲突和变化。产出不匹配时标记失败，重新打开依赖它的后续工作。
2. **前提审计**：来源区分 `given` 给定、`inferred` 推断、`assumed` 假设；验证状态另记 `verified/unverified/refuted`。给定不等于已证实。查证关键版本、接口、事实、单位与安全条件；无法验证的事项保留为显式结论条件。
3. **专项复核**：只启用相关检查。代码修改仍覆盖控制流、数据依赖、边界和意图对齐，小改动无需四行正式报告。其他专项见下表。
4. **恢复分支**：缺乏证据先查证，粒度过粗就拆分，局部缺陷定向修复，反复多维失败回到设计，无法验证则条件化或停止。默认同一失败最多两次局部修复，然后重新设计一次或报告阻塞；可按任务调整，不能靠改名重置预算。

## 按需专项

| 专项 | 核实内容 |
| --- | --- |
| 深层缺陷 `debug` | 最小复现、调用与数据流、状态不变量、失败原因和回归测试 |
| 性能 `performance` | 工作负载、基线、容量、延迟分位、资源与错误预算；没有测量不宣称提速 |
| 并发 `concurrency` | 共享状态、交错执行、重复请求、幂等、取消和资源释放 |
| 视觉交互 `visual` | 真实渲染、相关尺寸、内容状态、键盘与焦点、主流程；区分客观缺陷与审美偏好 |
| 内容 `content` | 事实来源、时效、数字单位、文档一致性及受众目标 |

详见 [专项检查指南](review-profiles.md)。这些是指导检查的流程，不是自动调优器或视觉评分器。无法检查时标注 `not_run`；若仍交付，则明确条件和限制，不伪报通过。

优先复用现有规范、测试和工具。仅在有实际风险且现有证据不足时新增测试；不要为了几行可控代码堆出大量非产品代码。

## 可选机械校验

文字表格通常足够，只有需要持久化或机械校验时才使用 [状态格式](state-format.md)。`audit_state.py` 检查结构与声明状态；`check_python.py` 仅做有限 Python AST 提示；`review_diff.py` 标记范围与差异风险。脚本要求 Python 3.10+，只读、不执行目标代码。退出码 0 是有限范围内无发现，1 是需处理发现，2 是输入或工具错误。

交付时先给结果，再给实际检查与重要限制。研究支持问题的存在，不证明该 skill 已达到某个准确率；真实任务记录不要进入公开发布包。
